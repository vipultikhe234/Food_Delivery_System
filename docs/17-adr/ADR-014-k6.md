# ADR-014: k6 as primary performance testing tool
- Status: Accepted
- Date: 2026-10-01
- Related requirements: REQ-QA-003, NFR-PERF-*, NFR-SCALE-*

## Context
The brief lists JMeter, k6 and Gatling. One primary tool keeps scripts, reports and CI integration consistent.

## Decision
- Use **k6** for HTTP and WebSocket load scenarios, with scripts in `tests/performance/`.
- Thresholds encode the NFR targets (for example `http_req_duration{name:menu}: p(95)<300`).
- Results are exported to Prometheus/Grafana and stored as report artefacts per run.
- JMeter or Gatling may be used only for a scenario k6 cannot express, and only with a recorded reason.

## Consequences
### Positive
- Scripts are JavaScript, close to the frontend team's skills. Thresholds act as pass/fail gates in CI. Native WebSocket support.

### Negative / risks
- Distributed load generation at very high RPS needs k6 Cloud or k6-operator. Not needed for the portfolio verification level (OQ-01).

## Alternatives considered
- **JMeter:** GUI-centric, XML scripts.
- **Gatling:** strong reports, but Scala/Java DSL and less natural WebSocket scripting.
